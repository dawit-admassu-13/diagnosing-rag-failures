# Human Audit Protocol — 70-Item Error Analysis Sample

Status: protocol only. No human labels exist yet. This document tells the
human PI (Rufael) exactly how to audit the existing AI-assisted first-pass
labels in `error_log_template.csv`. Nothing in this document is itself a
labeling result — running the audit is a manual step the PI must perform.

## 1. Purpose

The 70-item error analysis reported in the paper (Section 5.3, "Manual Error
Analysis") was labeled by an AI assistant, not the human author. The paper
already discloses this and recommends a human audit before the labels or the
qualitative patterns drawn from them are treated as validated evidence. This
protocol defines that audit so it is:

- **Blind first, reconciled second** — the PI labels each item without seeing
  the AI's label, to avoid anchoring on it.
- **Measurable** — agreement between the AI's first pass and the PI's
  independent labels is reported as a number (percent agreement + Cohen's
  kappa), not just a qualitative impression.
- **Actionable** — the outcome determines, via fixed decision rules
  (Section 6 below), exactly how Section 5.3 of the paper should be revised.

## 2. Scope

- Same 70 items already sampled (5 questions × 7 mode/condition groups × 2
  models = 70). No new sampling. The stratification is documented in the
  paper (Section 5.3) and in `error_log_template.csv`.
- All 70 items should be audited if time allows (~3 hours; see Section 7). If
  time is constrained, a partial audit of a random 20-item subset (stratified
  proportionally across the 7 mode/condition groups and both models) is an
  acceptable minimum — see Section 6.4 for how a partial audit changes what
  can be claimed.

## 4. Procedure (per item, blind pass)

For each of the 70 rows in `error_log_blind_for_audit.csv`:

1. Read `question`, `generated_answer`, and `reference_answer` in that row.
2. Open the exact context the model actually received:
   `rag_eval/logs/raw_calls/{model}/{condition}/{item_id}/trial_{trial}.json`
   — the `prompt` field is the literal text sent to the model (context +
   question); `retrieval_log_path` in the same JSON points to the full
   retrieval record if you want the passage scores as well. Do not rely on
   `retrieved_passage_ids` alone for this judgment — it lists IDs, not text.
3. Assign exactly one label from `labeling_rubric.md`'s table
   (`grounded_correct`, `grounded_incorrect`, `ungrounded_correct`,
   `ungrounded_hallucinated`, `partial_grounding`, `refused_abstained`,
   `retrieval_failure_not_model_fault`, or `other`) into `human_label`.
4. Write a short free-text justification in `human_rater_notes` — enough
   that someone re-checking your work later can see why you chose that label
   without re-deriving it from scratch.
5. Fill in `human_rater_id` (e.g., "Rufael — human PI") and
   `human_date_labeled` for every row.
6. **Do not open `error_log_template.csv` or look at the AI's label/notes
   until every row in the blind sheet is filled in.** This is the whole
   point of the blind pass — reviewing the AI's label first would bias your
   independent judgment and invalidate the agreement statistic in Section 5.

Save the completed file as `error_log_blind_for_audit.csv` (overwrite in
place) once all 70 rows have a `human_label`.

## 5. Reconciliation (after the blind pass is fully complete)

Only after step 4 is 100% done, merge the two files on `item_id` + `model` +
`condition` + `trial` to produce `error_log_audit_reconciled.csv` with these
columns:

```
item_id, model, condition, trial, question,
ai_label, ai_rater_notes,
human_label, human_rater_notes, human_rater_id, human_date_labeled,
agree (TRUE/FALSE, ai_label == human_label),
final_label (defaults to human_label; override manually only with a written
             reason in adjudication_notes),
adjudication_notes
```

This merge is a mechanical join — do not hand-edit `ai_label` or
`ai_rater_notes` (they are the historical record of what the AI actually
said) or `human_label` (it is the record of your independent judgment).
Disagreements are resolved only in `final_label` + `adjudication_notes`, so
both original judgments remain visible and auditable.

For any row where `agree = FALSE`, re-read the item once more with both
labels in front of you and decide `final_label`: usually the human label
wins (the PI is the ground-truth rater here), but if on reflection you think
the AI's label was actually more defensible, keep it as `final_label` and
say why in `adjudication_notes` — don't silently discard a disagreement in
either direction.

## 6. Computing agreement and deciding what it means for the paper

### 6.1 Metrics to compute

- **Percent agreement** = rows where `agree = TRUE` / 70.
- **Cohen's kappa** between `ai_label` and `human_label` (accounts for
  agreement expected by chance given the label distribution; percent
  agreement alone is not enough with 6-8 possible categories and an uneven
  label distribution like this sample's). Compute once overall, and again
  separately for Claude-only rows (n=35) and Llama-only rows (n=35) if you
  want to check whether the AI's labels were more reliable for one model
  than the other.
- Interpretation scale (Landis & Koch 1977, the standard reference for
  kappa): <0.00 poor, 0.00–0.20 slight, 0.21–0.40 fair, 0.41–0.60 moderate,
  0.61–0.80 substantial, 0.81–1.00 almost perfect.

### 6.2 Decision rules for revising Section 5.3

| Outcome | Required paper action |
|---|---|
| Kappa ≥ 0.61 (substantial/almost perfect) | Keep the AI-assisted labels and the existing qualitative bullets in Section 5.3. Add one sentence reporting the audit: "A human audit of this subsample by the paper's author found substantial agreement with the AI-assisted first-pass labels (κ = X, Y% exact agreement)," with a citation-free inline number. Remove or soften the "recommend a human audit" hedge since it has now been done. |
| Kappa 0.21–0.60 (fair/moderate) | Recompute the label-distribution percentages in Section 5.3 using `final_label` instead of the AI's original labels, and rewrite the three bullet-point qualitative findings using only items where `final_label` supports them (drop or re-verify any bullet whose supporting item(s) flipped label). Report both kappa and the revised percentages, and keep language explicit that labels were human-corrected after an imperfect first pass. |
| Kappa ≤ 0.20 (slight/poor) or you judge the AI labels unreliable on inspection | Do not report the AI-assisted label distribution as a finding at all. Rewrite Section 5.3 around `final_label` only (fully human-labeled), state plainly that the AI first pass was found unreliable on audit and was superseded, and consider whether 70 items is still enough for the qualitative bullets or whether a larger human-only pass is warranted before v2 is finalized. |

### 6.3 If you disagree with a rule above in a specific case

These are defaults, not a substitute for judgment. In particular, Section
5.3's three qualitative bullets each rest on a small number of specific
items (matched Claude/Llama pairs on Retrieval Noise items for bullet 1;
two matched Retrieval-Blindness/Evidence-Ignorance-removed items for bullet
2; at least one item with identical top-5 retrieval between clean and blind
conditions for bullet 3). If any of those underlying items flip label during
reconciliation, re-check and, if necessary, correct or remove the specific
bullet regardless of the aggregate kappa — a high overall kappa does not
protect a bullet built on an item that individually flipped.

### 6.4 If you only audited a 20-item subset

Report the subset size explicitly alongside kappa (e.g., "audited on a
random 20-item subset stratified across mode/condition/model, κ = X"). Do
not apply the aggregate percentages from `error_log_template.csv` as if the
full 70 items were validated — only claim what the audited subset supports,
and keep the "AI-assisted, preliminary, not independently validated for the
full sample" caveat for the remaining 50 items.

## 7. Logistics

- Estimated time: ~2–3 minutes per item for a careful read of question +
  context + answer + rubric lookup → roughly 2.5–3.5 hours for all 70 items
  in one sitting, or split across 2–3 sessions (record `human_date_labeled`
  per row so a multi-session audit is still traceable).
- Do the blind pass in one sitting per session if possible — stopping
  mid-session and resuming later is fine, but do not go back and re-read
  rows you've already labeled once you've started reconciliation.
- If a `retrieval_log_path` or `raw_calls` file is missing for a row (should
  not happen — all 900 calls are logged — but verify), flag it in
  `human_rater_notes` as `MISSING SOURCE` rather than guessing.

## 8. Deliverables this protocol expects back

1. `error_log_blind_for_audit.csv` — completed with all `human_*` columns
   filled in (or the audited subset, if partial).
2. `error_log_audit_reconciled.csv` — the merged file from Section 5.
3. The computed percent agreement and Cohen's kappa (overall + per model),
   reported wherever the paper's Section 5.3 cites the audit.
4. A one- or two-sentence note on which decision-rule tier (Section 6.2)
   applied, so the next paper-editing pass knows exactly what to change.

Only once items 1–4 exist should Section 5.3 of the paper (and its
"AI-assisted... human PI audit... recommended" hedge) be revised. Until then,
the paper's current language — that the error analysis is a first-pass,
AI-assisted signal pending human audit — remains accurate and should not be
changed.
